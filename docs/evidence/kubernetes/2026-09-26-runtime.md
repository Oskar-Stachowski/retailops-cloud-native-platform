## Verified behavior

| Check | Result in both runs |
|---|---|
| Startup | PostgreSQL, broker, API, frontend and consumer ready; migration, seed and six-topic initialization Jobs completed. |
| Ingress and UI | Traefik to frontend Nginx to API; named-host routing, dashboard, Product 360, decisions and browser reloads passed. |
| NetworkPolicy | Unlabelled Pod and foreign namespace blocked; allowed same-Pod control passed using direct Service IPs. |
| Streaming | Two deliveries of one sales event produced one stored processed event and three metric rows; live API reflected it. |
| Database outage | Direct `/health` returned 200, `/ready` returned 503, and API Services had zero ready endpoints. |
| Persistence | PostgreSQL replacement used the same PVC; all compared data survived. Broker retained all six topics and the published message after restart. |
| Workload restart | API, frontend, consumer and broker recovered; HTTP/browser checks, decisions and idempotent replay passed. |
| Update and rollback | Five validation stages passed; actual HTTP 504 detected during injected API outage; previous images restored service. |
| New writes | A comment after update survived rollback; a second comment after rollback succeeded. |
| Cleanup | Generated cluster, temporary credentials/kubeconfig and local test image tags removed; cleanup passed. |

The five stages are `previous`, `database_restarted`, `workloads_restarted`,
`upgraded` and `rolled_back`. Each checks HTTP health/readiness, three business
decisions, five idempotent actions, database integrity and the browser journeys.

There are 15 public tables. Row fingerprints cover 14 tables: only
`realtime_consumer_state` row data is excluded because restart counters and
timestamps change intentionally. Schema and sequence checks still cover the
database; this fixture has no sequences. The 70 compared rows remained identical
through restart and update. The update comment increased the count to 72, which
survived rollback; the final write increased it to 74. Audit records, stored
events and metric observations are included. The migration head stayed
`6b0f1c2d3e4a`, with no downgrade, database restore or reseed during rollback.

## Evidence integrity and limits

The downloaded CI ZIP matched SHA-256
`3be3d0c970796e21288a36b3bafe1014545a32a2e31b952e9d998165523efb2f`.
The tracked JSON preserves each source report's checksum, script hashes,
architecture, exact image IDs, stage results, initial/final table fingerprints,
timings, cleanup and all 24 CI job conclusions. It omits raw logs, machine IDs,
Pod UUIDs and random local image tags. Builder-only `validation` placeholders
are not runtime outcomes; the successful checks are recorded under `stages`.

Earlier diagnostic runs found startup, image-import, ingress RBAC and timeout
issues that were fixed in PR #45. Only the final clean local run and successful
CI run above are presented as passing evidence. Final local inspection found no
kind clusters or test image tags; the current context remained `cka-services`.

This proves a local single-node development deployment, including PVC retention
across Pod replacement. It does not prove storage recovery after cluster/host
loss or HA. The two application source trees under `services/api` and `frontend`
are identical; the test establishes deployment and persistence mechanics with
unchanged migration history, not compatibility of future business-code or schema
changes. Timings use a small demo fixture and are not production RTO/RPO.

These native source builds are distinct from the signed AMD64 GHCR v0.2.1
artifacts verified in [step 3](../releases/2026-09-26-registry.md). No native ARM64
registry release, EKS deployment, Helm release, production authentication or
RetailOps AI implementation is claimed.
